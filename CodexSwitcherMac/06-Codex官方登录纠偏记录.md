# Codex 官方登录纠偏记录

## 1. 背景

本次纠偏来自账号中心“开始官方登录”入口误触发其他供应商登录页的问题。项目目标一直是 Codex 账号登录，因此登录、绑定、校验、切换都必须收敛到 Codex 官方登录链路。

## 2. 本次更正

- 登录入口只执行 `codex login`
- 登录状态检测只执行 `codex login status`
- App 会优先解析 Codex CLI 绝对路径，例如 `/Applications/Codex.app/Contents/Resources/codex`，避免 GUI App 和 Terminal 的 PATH 不一致导致 `command not found`
- 配置目录只读取 `CODEX_HOME` 或默认 `~/.codex`
- 登录凭证只识别 `~/.codex/auth.json`
- 登录完成后，`~/.codex/auth.json` 中的 `auth_mode = chatgpt` 是强事实来源；即使某次 CLI stdout 没及时返回 `Logged in`，App 也应承认该 Codex 官方登录态
- 真实账号绑定只接受 `auth_mode = chatgpt` 的 Codex 官方账号登录态
- App 会从 Codex `id_token` 中解析邮箱并写入 `account_email`，账号中心和仪表盘必须显示“登录账号：邮箱”
- `profile_ref` 保留给官方 `account_id`，用于后续真实额度请求头，不再用来展示邮箱
- 页面必须同时展示“当前官方登录态”和“已绑定账号列表”；当用户刚登录新账号但尚未绑定时，应明确显示该邮箱并提示一键绑定
- `api_key`、其他供应商登录态、历史本地演示账号都不能作为“真实 Codex 账号绑定”通过

## 3. 当前主流程

1. 用户在账号中心点击“开始官方登录”
2. App 在 Terminal 中打开 `codex login`
3. 用户按 Codex CLI 官方流程完成 ChatGPT/Codex 账号登录
4. 用户回到 App 点击“绑定当前已登录账号”
5. Rust 侧执行 `codex login status`，并读取 `~/.codex/auth.json`
6. 校验 `auth_mode = chatgpt`
7. 敏感会话材料写入 macOS Keychain
8. SQLite 只保存账号元信息、Keychain 引用和验证状态

## 4. 明确禁止

- 不允许再调用其他供应商 CLI 登录命令
- 不允许把 API key 登录态当作 Plus/Codex 账号登录态
- 不允许把演示账号、演示快照或本地推断数据作为真实账号数据
- 不允许在拿不到真实额度时补假百分比

## 5. UI 文案要求

- 主按钮文案保持为“开始官方登录”
- 诊断结果必须显示“Codex 配置目录”和“Codex 登录凭证”
- 无真实额度时显示“未知”
- 额度百分比必须明确标注为“已用”，不能让用户误以为是剩余额度
- 恢复时间必须分开显示 `5h 预计恢复` 和 `7d 预计恢复`
- 账号列表只展示真实绑定账号

## 6. 验收标准

- 点击“开始官方登录”后，Terminal 中运行的是 `codex login`
- Terminal 命令必须使用 Codex CLI 绝对路径，不允许只写裸 `codex`
- 不再打开其他供应商登录页
- `codex login status` 显示已登录后，App 可绑定当前 Codex 账号
- 非 `chatgpt` 登录模式不能通过真实账号校验
- 绑定或验证后，账号卡片能显示当前登录的账号邮箱
- 文档、UI 和 Rust 命令均使用 Codex 官方登录口径

## 7. 2026-04-18 真实采样修复补充

### 7.1 Keychain 读取回退策略

为避免已绑定账号因为旧 `session_ref` 或缺失的 Keychain 项导致“立即采样”失败，真实采样链路新增以下回退策略：

1. 优先按 `session_ref` 读取绑定会话
2. 若失败，则按稳定 `account_key` 对应的 Keychain 项再次读取
3. 若当前官方登录态与该账号的 `account_id` / `account_email` 一致，则允许使用当前 live session 自动补回缺失的 Keychain 项

### 7.2 多账号绑定约束

多账号绑定不再允许仅凭“同昵称”覆盖旧账号；优先级必须是：

1. `account_key`
2. `account_email`
3. `profile_ref`（官方 `account_id`）

只有历史残留账号缺少邮箱和官方账号 ID 时，才允许用同昵称做一次性兼容迁移。

## 8. 2026-04-18 多账号一致性修复

### 8.1 验证账号的约束

`验证账号` 现在只负责判断“这张账号卡绑定的会话是否等于当前官方登录态”，不再在 mismatch 场景下把当前登录邮箱和官方账号 ID 写回目标账号。

### 8.2 切换后的身份同步

真实切换成功后，目标账号会同步当前官方登录态的身份字段，用于保证后续“立即采样”与当前活跃账号一致。

### 8.3 历史脏数据自愈

系统启动时会尝试读取每张真实账号卡的绑定会话：

- 如果能读到真实身份，则回填 `profile_ref / account_email`
- 如果发现会话内容与 `account_key` 锚定的官方账号 ID 不一致，则把该账号标记为 `会话不匹配`，并清空错误邮箱，避免两张卡显示成同一个账号

### 8.4 一键重绑流

账号中心为 `登录失效 / 会话不匹配` 的账号新增两条修复路径：

- `重新登录并重绑`：打开 Codex 官方登录流程，登录完成后自动尝试重绑当前账号卡
- `按当前登录态重绑`：直接把当前已登录的官方会话重绑到这张账号卡

## 9. 2026-04-18 仪表盘与切换采样闭环补充

### 9.1 首页身份展示调整

仪表盘首页和账号总览卡片不再把 `profile_ref` 回退显示到“登录账号”位置，避免把官方账号 ID 误当成邮箱。

当前统一规则：

- `登录邮箱` 只展示 `account_email`
- `官方账号 ID` 只展示 `profile_ref`
- 两个字段必须同时展示，缺失时明确显示“未读取到邮箱”或 `--`

### 9.2 账号总览卡片补齐真实指标

账号总览区已改为图卡式结构，每张真实账号卡都直接显示：

- `5h 已用`
- `7d 已用`
- `5h 预计恢复`
- `7d 预计恢复`

这些数据来自各账号自己的最新真实快照，不再只显示当前活跃账号的快照。

### 9.3 多账号采样逻辑修正

此前的 bug 是：系统会拿“当前 live 登录态”去校验所有账号，导致只要用户登录了 `2027`，`2026` 就可能被误判为 `会话不匹配`。

现已调整为：

1. 当前 live 账号优先使用当前 live session 采样
2. 非当前账号优先读取各自绑定的 Keychain / 会话快照
3. 只有当绑定快照内容与该账号自己的稳定身份锚点不一致时，才标记为 `会话不匹配`

### 9.4 当场实测结果

本轮已完成下面这条真实主路径：

1. `2027` 账号重新登录并重绑成功
2. 页面显示 `demo2027@example.com` 与官方账号 ID `00000000-0000-4000-8000-000000000001`
3. `2026` 账号重新登录并重绑成功
4. 从 `2027` 真实切换到 `2026`
5. 切换后再次点击“立即采样”
6. 首页继续稳定显示 `2026` 的邮箱、官方账号 ID、`5h 已用 89%`、`7d 已用 81%`、`5h 恢复 2026-04-18 23:49:27`、`7d 恢复 2026-04-24 11:21:15`

结论：本轮“真实重绑 -> 真实切换 -> 立即采样”主路径已闭环，采样结果不再回刷成上一个账号。

## 11. 2026-04-18 验证账号语义与误点保护

### 11.1 验证账号的定义

`验证账号` 只做一件事：

> 校验“当前 Codex 官方登录态”是否就是这张账号卡绑定的账号。

它不是重新绑定，也不是把当前官方登录态写入目标账号卡。

### 11.2 新保护规则

为避免用户当前登录 `Gmail` 时误点 `2027` 的 `验证账号`，导致目标账号被标记为 `会话不匹配`，现在增加双层保护：

1. 前端判断当前官方登录态的邮箱 / 官方账号 ID 是否匹配目标账号卡
2. 不匹配时，按钮显示 `需先登录该账号` 并禁用
3. 后端再次校验，不匹配时直接返回错误提示
4. 后端不再在这种误点场景下写入 `mismatch`、不修改目标账号卡状态

### 11.3 推荐操作分工

- `验证账号`：当前已经登录这张卡对应账号时使用
- `重新登录并重绑`：当前没有登录这张卡对应账号，或这张卡会话已失效时使用
- `按当前登录态重绑`：确认当前官方登录态就是要绑定到这张卡时使用

## 12. 2026-04-18 切换并采样、账号操作文案与排序收敛

### 12.1 切换成功后自动采样

`切换账号` 主动作已收敛为 `切换并采样`。

新的行为是：

1. 后端先完成真实账号切换与切换后校验
2. 切换成功后立即触发一次真实用量采样
3. 采样成功时写入 `切换后自动采样完成` 通知
4. 采样失败时不回滚已成功的账号切换，只写入 `切换后自动采样失败` 通知
5. 前端收到最新 `DashboardOverview` 后同步刷新活跃账号、账号列表、首页用量卡与通知中心

这样可以避免“切换成功后还停留在上一账号采样结果”的误解，同时保留真实采样失败时的可诊断信息。

### 12.2 账号操作文案收敛

本轮将容易误解的账号操作统一成更明确的动作语义：

- `校验当前登录态`：只校验当前 Codex 官方登录态是否匹配这张账号卡，不做切换、不做重绑
- `需先登录该账号`：当前官方登录态不是这张账号卡，禁止误校验
- `切换并采样`：切到该账号后自动刷新真实用量
- `当前账号`：该账号已经是当前活跃账号
- `重新登录并重绑`：用于登录失效或需要重新走官方登录的账号卡
- `按当前登录态重绑`：确认当前官方登录态就是目标账号时，才把当前登录态绑定到这张卡

### 12.3 账号排序规则

账号列表和仪表盘账号总览统一使用同一套排序：

1. 当前活跃账号置顶
2. 可切换账号排在前面
3. 登录失效、会话不匹配、异常账号随后展示，方便修复
4. 耗尽窗口账号再后展示
5. 同一优先级内默认账号优先，再按昵称排序

### 12.4 交互提示规则

账号卡底部始终展示操作建议：

- 当前账号且官方登录态一致：提示可直接采样，校验按钮只用于确认当前登录态
- 当前账号但官方登录态不一致：提示先重新登录并重绑
- 可切换账号：提示点击 `切换并采样` 后会自动刷新真实用量
- 会话不匹配：提示先登录这张卡对应账号，再重绑或修复
- 登录失效：提示使用 `重新登录并重绑`
- 未确认有效性：当前登录态匹配时才允许 `校验当前登录态`

## 13. 2026-04-18 一键重绑闭环与采样失败诊断卡

### 13.1 重新登录并重绑一键闭环

`重新登录并重绑` 已从“打开登录后用户手动回 App 操作”收敛为等待式闭环：

1. 用户在目标账号卡点击 `重新登录并重绑`
2. App 记录待修复账号 ID，并打开 Codex 官方登录流程
3. App 返回前台或定时刷新后读取当前 Codex 官方登录态
4. 只有当前官方登录态匹配目标账号卡的登录邮箱或官方账号 ID 时，才自动执行重绑
5. 如果当前登录态不是目标账号，App 会继续等待，并提示需要登录的目标账号
6. 用户可点击 `取消等待` 中止本轮自动重绑

### 13.2 防误绑保护

本轮增加前后端双层保护：

- 前端：`按当前登录态重绑` 前先判断当前官方登录态是否匹配目标账号卡
- 后端：`repair_account_auth` 再次调用身份校验，防止绕过前端时把错误官方登录态写入目标账号
- 不匹配时不会更新账号卡的邮箱、官方账号 ID、Keychain 会话引用或账号状态

### 13.3 采样失败诊断卡

账号中心新增 `采样失败诊断卡`，用于把技术错误翻译成下一步动作：

- Keychain item not found：提示使用 `重新登录并重绑` 重建安全凭证
- 当前官方登录态不一致：提示先切到目标邮箱，再等待自动重绑
- Codex CLI / 登录状态不可用：提示先开始官方登录，再更新诊断
- 真实额度暂不可读：提示稍后重试采样或查看登录态诊断

诊断卡同时展示：

- 最近错误
- 建议动作
- 当前官方登录态
- 当前登录态是否已绑定到账号列表
- `更新诊断` 与 `刷新状态` 快捷按钮

### 13.4 诊断绑定环境修正

`诊断绑定环境` 现在会结合本地账号列表判断 `current_is_bound`，不再固定返回未绑定。这样可以更准确地区分：

- 当前官方登录态已在账号列表中
- 当前官方登录态未绑定
- 当前未检测到官方登录态

- 已完成：切换前登录态读取、目标账号可切换校验、目标账号邮箱与官方账号 ID

## 17. 2026-04-19 自动刷新与智能自动采样

## 18. 2026-04-19 Menubar 常驻采样与双窗口额度判定

### 18.1 变更背景

上一版自动采样仍由前端页面调度，窗口关闭后无法保证继续运行；同时账号风险状态主要按 `5h 已用` 判定，导致 `7d 已用 = 100%` 的账号仍可能被错误显示为健康。

这一轮把这两条主路径收敛到后端：

- 自动采样由 Tauri / Rust 后台线程负责。
- 风险状态统一按 `max(5h 已用, 7d 已用)` 判定。

### 18.2 双窗口额度判定规则

风险状态现在改为：

- 任一窗口 `>= 100%`：`不可用 exhausted`
- 任一窗口 `>= 85%` 且 `< 100%`：`预警 warning`
- 两个窗口都 `< 85%`：`健康 healthy`

这意味着：

- `5h 已用 = 100%` 时不可切换。
- `7d 已用 = 100%` 时同样不可切换。
- 账号中心、仪表盘、时间轴、推荐动作和切换校验都会同步使用这套规则。

### 18.3 关闭窗口后继续采样

自动采样已从前端 `useEffect` 调度迁移到 Rust 后台线程。

现在行为改为：

- App 启动后启动后台采样循环。
- 后台按 `check_interval` 读取设置并定时采样。
- 如果开启“关闭窗口后继续采样”，即使主窗口关闭，只要 App 仍在 Menubar 中，后台仍会继续采样当前活跃账号。
- 自动采样仍只针对当前活跃账号，不会自动切换账号。

### 18.4 窗口关闭行为

点击主窗口关闭按钮后：

- 不退出 App。
- 主窗口隐藏。
- Menubar 继续保留。
- 后台自动采样继续运行。

真正退出仍通过系统退出或 Menubar 菜单完成。

### 18.5 设置页调整

设置页的原开关 `仅前台自动采样` 已收敛为更直观的文案：

- `关闭窗口后继续采样`

当前策略说明也同步修改为：

- `关闭窗口后继续采样（Menubar 保持运行）`
- 或 `仅窗口可见时采样`

并将当前默认值调整为允许关闭窗口后继续采样。
